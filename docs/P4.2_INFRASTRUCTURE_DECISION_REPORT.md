## 2. Recommended option (single coherent recommendation)

**GCP with Terraform**, targeting:

- **Runtime:** Cloud Run (container backend) + static/nginx frontend hosting
  behind the same Cloud Run or a simple static bucket + LB; container already
  reads `$PORT`, is non-root, and has a `/health` probe — Cloud Run is the
  smallest delta from the current Dockerfile.
- **Database:** Cloud SQL (PostgreSQL 16) — managed PITR, private networking,
  automatic maintenance.
- **Redis:** Memorystore for Redis — managed, TLS-capable, supports the P4.4
  distributed rate limiter.
- **Secrets:** Secret Manager, referenced by the runtime; never in the repo.
- **IAM:** Workload Identity Federation from GitHub Actions + dedicated
  service accounts per environment (staging, production) with least-privilege
  roles (Cloud Run invoker/developer, Cloud SQL client, Memorystore user,
  Secret Manager secretAccessor).
- **TLS/domain:** Cloud Run managed TLS with a custom domain
  (`app.<company>.com` for production, `staging.<company>.com` for staging).
- **Environments:** Terraform modules parameterized by `staging` / `production`;
  both provisioned from the same code with separate state backends.

Rationale: the repository is already Cloud Run-shaped (port contract, health
endpoint, 12-factor env config), GCP stubs exist, and the ROADMAP prefers
Terraform. This minimizes rework and operator learning.

## 3. Alternatives (and why not chosen)

- **GKE:** overkill for a single service; adds cluster ops, node security, and
  cost. Cloud Run provides the same containers with far less operator burden.
- **AWS (ECS/App Runner + RDS + ElastiCache + Secrets Manager):** fully viable,
  but would rewrite the provider stubs and add new operational context with no
  repository signal.
- **Azure (Container Apps + Flexible Server + Cache):** viable; same
  "no signal" objection as AWS.
- **Plain VPS + Docker Compose + managed-free Postgres:** cheapest, but loses
  managed PITR, managed TLS, IAM, and the ROADMAP MUSTs (IaC, secrets,
  backups); not recommended for real users/money.

## 4. Impact analysis

| Area | Cloud Run + Cloud SQL + Memorystore (recommended) | Alternatives |
|---|---|---|
| **Cost** | Pay-per-request compute; managed Postgres/Redis tiers dominate cost; PITR adds storage. Staging can run smaller tiers / scaled-to-zero. | GKE/AWS/Azure add management + instance cost; VPS is cheapest but adds human ops cost and risk. |
| **Security** | Managed TLS, Workload Identity (no long-lived keys), private networking for DB/Redis, least-privilege SAs, Secret Manager. | VPS requires operator-managed TLS, firewalls, key rotation; more surface. |
| **Operations** | Managed patching/HA for DB/Redis; Cloud Run autoscaling; no VM management; deploy = image + revision. | GKE/AWS/Azure have more moving parts; VPS needs full sysadmin. |
| **Deployment** | Terraform provisions; CI/CD (P4.1 + later cd.yml) deploys images; migrations as a pre-deploy step. | Provider-specific pipelines diverge; VPS needs bespoke deploy scripts. |
| **Portability** | Container + 12-factor env keeps the door open to move; Terraform abstracts provider resources. | Cloud Run YAML alone is less portable than Terraform. |

## 5. Managed PostgreSQL design (once D1/D3 approved)

- Cloud SQL PostgreSQL 16 (match dev), private IP, no public access.
- PITR enabled before first production deploy; automated daily backups;
  restore drill during P4.6.
- Dedicated DB user for the app with least privilege; migration user separate
  or same with restricted network.
- Connection via `DATABASE_URL` from env (Secret Manager holds credentials).

## 6. Managed Redis design (once D1/D4 approved)

- Memorystore (or chosen provider) instance; private network; TLS enabled;
  no public endpoint.
- Consumed by P4.4 (distributed rate limiting) and optional future jobs.
- `REDIS_URL` provided via env/Secret Manager.

## 7. Container / runtime choice

- Keep the existing multi-stage non-root Dockerfile; Cloud Run is the
  recommended runtime (port contract + `/health` already satisfied).
- Frontend: build static assets at deploy; serve via a minimal nginx container
  on Cloud Run or a bucket+LB — decision D1/D9 confirms.
- No host-port exposure for Postgres/Redis in staging/production.

## 8. Networking / TLS / domain

- Cloud Run managed TLS (recommended) with `app.<company>.com` (production)
  and `staging.<company>.com` (staging); CORS origin per environment.
- Private VPC (or serverless VPC access) so the app reaches Cloud SQL and
  Memorystore over private IPs; DB/Redis never publicly reachable.
- Google OAuth production redirect URI will be the production frontend origin
  (must be added to the OAuth client after D6).

## 9. Backup / PITR implications

- Managed PITR is a P0 (ROADMAP MUST). Restore = provider console/`gcloud`
  point-in-time restore into a new instance; a scripted restore drill belongs
  to P4.6.
- Dev/local data (Compose volume, Homebrew Postgres) is explicitly NOT
  production data and is outside this design.

## 10. IAM / service-account model

- One service account per environment (staging, production) with only the
  roles needed to run: Cloud Run service identity, Cloud SQL Client,
  Memorystore (or equivalent), Secret Manager secretAccessor.
- GitHub Actions uses Workload Identity Federation to assume a short-lived
  per-environment deploy identity — no long-lived keys in CI.
- Operators authenticate via their own IAM accounts; no shared keys.

## 11. Staging vs production topology

- Terraform modules `infra/terraform/modules/ice` instantiated twice:
  `infra/terraform/environments/staging` and `.../production`, each with its
  own state backend, VPC/project isolation (or at minimum environment-tagged
  resources), its own Cloud SQL/Memorystore/Secret Manager namespace, and its
  own Google OAuth client/redirect URI.
- Staging mirrors production shape at smaller scale; it is the P4.6 UAT and
  rollback-rehearsal surface.
